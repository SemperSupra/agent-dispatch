Product source authority [Mail Evidence #4](https://github.com/SupraShellScripts/mail-evidence-private/issues/4), experimental owner [#39](https://github.com/SupraShellScripts/mail-evidence-private/issues/39). Builds upon already merged [original XTDB R2 PR #870](https://github.com/SemperSupra/agent-dispatch/pull/870), which qualified three distinct source occurrences, an XTDB valid-time upsert, historic system records, and disk-backed restart. **This R3 tests a different, stronger proposition: preservation of the same six fictional source occurrences/six claims and eight time-scoped outcomes that native SQLite/official PostgreSQL previously tested.**

## Exact reusable assets and cost boundary

- Original XTDB source/rights and immutable snapshot image: MPL-2.0, `ghcr.io/xtdb/xtdb@sha256:aa7483e48674446a4892e0ea56a0953502fa5ccb9c4c803a9fb569ea5f0c28fe`. This is an upstream development **snapshot**, not XTDB 2.2.0 release qualification.
- Original PostgreSQL-wire client: pinned official `postgres:18.7-trixie@sha256:e754b839f447639b7004895f4d8a4bfcb4e9dbe3a1bc035f27f646562a16fd61`.
- Execution: standard public GitHub Ubuntu x64, existing fixed typed workload `requests/gha/mail-xtdb-frozen-oracle-r3.json`, zero cost declared, one attempt, max 235-second internal and 8-minute parent job. No private GitHub Actions, user mail, source-derived hashes, paid model inference, credentials, new workflow, cron or general shell dispatch. A private `--internal` Docker bridge connects only the two ephemeral reviewed image digests; XTDB runs 2 CPU/3 GiB/256 PID and no host-published ports. On exit, both network and data volume are discarded.
- Input: import literal `SOURCE_ROWS`, `CLAIM_ROWS` and source digests from the existing SQLite R1's frozen fictional fixture; independently freeze **eight expected statuses and exact original source ID sets**, not dynamically derived from the database being measured.
- SQL: XTDB's real PGWire endpoint executes source/claim inserts and joined, tenant-filtered, modality-filtered queries over separately stored `valid_from`, `observed_at`, and `acquired_at`. All clock representations are canonical, fixed UTC RFC3339 strings, so lexical comparison is meaningful for **this fixture only**. These are **explicit SQL predicates**, not native `FOR SYSTEM_TIME AS OF` acquisition import semantics.
- Negative gates: late-arriving retroactive correction unavailable to earlier knowledge queries, duplicate acquired source rows remain distinct with one original lineage, planned future statement not an accomplished approval, cross-tenant beta not visible to alpha, stale/source-absent unknown, exact six-source/six-claim retention, exact status/source-ID oracle. Restart XTDB from same volume and rerun the late retrospective query; require identical result and original source count.

## Critical nonclaims and promotion vetoes

An XTDB `INSERT` against an existing `_id` may act as a valid-time upsert. Source-occurrence immutability is **NOT** enforced by this engine or demonstrated here, so explicit `xtdb_source_immutability_enforced=false` and `source_history_risk=XTDB_UPSERT_ID_REQUIRES_APPLICATION_GUARD` are part of the native receipt and verifier. Distinct immutable original occurrence IDs and a fail-closed adapter are mandatory before production. The same frozen eight queries prove **only explicit source/knowledge timestamp predicate parity**, not XTDB-native system-time semantics, post-hoc acquisition reassignment, automatic conflict resolution, native MAPI/PST, cross-account authorization or licensing/security attestation. There is no model, agent, or self-improving logic here.

Keep original source evidence immutable outside of XTDB; treat graph/DB entries as derived, rebuildable projections. Require a separate per-source upsert-negative test and a full PostgreSQL/XTDB/SQLite resource envelope before promotion. A first red CI result is a real experiment outcome and cannot be hidden by altering frozen expected results. After native first PASS, move the heavy two-image profile back to reviewed on-demand execution and preserve its source/verifier/receipts, avoiding recurring downloads in unrelated PRs.
