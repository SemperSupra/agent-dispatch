# MCP GHA — preregistered execution-topology qualification

**Authority:** public source-only synthetic transport RDTE in draft PR #555.
Real scientific protocol remains private Search Adapters #240 and CPE #229.
No new permanent host, scheduler, privilege or full CPE publication.

## Question

Does the compute topology introduce operational retrieval effects when both
the independent-reference and CPE-labelled **public synthetic** query plans
are fixed?

The comparison does **not** establish that a topology improves conceptual
recall or that synthetic Track B was actually generated by the private CPE.
Both public topology implementations run the exact same three-query per-arm
English/German/Thai canary against the exact same pinned SearXNG image,
settings file and source revision.

## Fixed treatments

| Arm | Plan input | Authority |
| --- | --- | --- |
| Reference | `pilot/arms/reference/plan.json` | Public synthetic independent reference probe |
| CPE-labelled | `pilot/arms/cpe/plan.json` | Synthetic CPE-labelled query fixture — NOT real CPE |

Topology **P**: two physically independent GitHub-hosted Ubuntu runners
started by one Actions matrix, concurrently. Each runner receives only one
arm manifest through non-cone exact-file sparse checkout, starts one fresh
local pinned SearXNG Docker container, executes Stage R, seals evidence
with a disposable test-only `age` recipient, locally decrypts the canary,
emits aggregate metrics, and deletes all local query/response material.

Topology **S**: one GitHub-hosted Ubuntu runner, sequential arm execution.
Sample a random initial order (A then B, or B then A), then repeat both
arms **in the opposite order** (AB/BA or BA/AB). Each arm/pass launches
a brand-new pinned SearXNG Docker container; it is stopped and discarded
before the next arm. Every raw response remains runner-local and is
deleted after synthetic, aggregate-only comparison.

Why **not** concurrent two-container same-VM as the default control:
simultaneous containers introduce CPU/RAM contention and possibly shared
egress/engine rate-limit coupling. Sequential counterbalanced order is a
more informative controlled baseline. A simultaneous shared-host experiment
can be added later as a third factor if the sequential-vs-distributed
comparison identifies an effect worth isolating.

## Primary measures

1. Native HTTP network attempts, provider-accepted vs failed responses.
   A 200 containing an error object is counted as a failure, not success.
2. Number of retrieved hits, distinct result URLs and distinct source hosts.
   Domain/URL counts are **coverage proxies**, never correctness metrics.
3. Per-query elapsed time and per-arm wall-clock time including disposable
   provider startup and cleanup.
4. After both tracks have frozen, URL overlap *proxy* between synthetic
   reference and CPE-labelled observations (single-runner control only).
   No URLs, query text, titles, snippets or private keys enter summaries.

## Invariants and threats to inference

- Pin **both** arm query fixtures; same locale fields, same query role,
  same 3-request budget, source image/config SHA and Go source revision.
- Do not claim that the external upstream search providers ran with
  identical corpus snapshots, egress IP, engine mix or throttling.
- Record run IDs, source SHA, runner/job identity, random order and the
  exact timestamp window when later adjudicating variability.
- A temporary GitHub-hosted VM is **not confidential computing**; only
  public-reviewed synthetic inputs are admitted. Output encryption is not
  private source-code execution.
- Matrix jobs isolate VM and checkout but do not guarantee experimental
  blindness, matching host hardware, exact source ancestry or validity.
- Randomizing order and counterbalancing mitigates—but does not eliminate—
  time/order confounding. The parallel arms may have different public
  egress IPs and provider refusal rates.
- Per-arm compare is **exploratory**; do not infer that one topology is
  "more accurate" from one pair of traces or retrieved hit count.
- No ephemeral-age test key or unsealed search responses are uploaded.
  Persistent **real** encrypted result artifacts require a separate
  private-key custodian, owner-approved permanent recipient and trusted
  private evidence ingestion.

## Native observations — 2026-10-27, initial repeats

**Source:** [GitHub Actions run 40484570739](https://github.com/SemperSupra/agent-dispatch/actions/runs/40484570739),
the first HEAD at `ab9b461b4334a5c184c42c6e47489b1595195e68`.
The parallel jobs were one set of independent VMs; only the single-VM
sequential control was rerun to sample a second random starting order.
All three native workcell modes passed. Total: 30/30 provider requests
accepted; no source rights, authentic CPE, blindness or semantic validity
was claimed.

| Workcell/attempt | Random first | Reference wall mean | CPE wall mean | Ref query sum mean | CPE query sum mean |
| --- | --- | ---: | ---: | ---: | ---: |
| Parallel distinct VMs, job 122123018627 / 122123019041 | concurrently | 29,383 ms | 36,306 ms | 3,438 ms | 2,689 ms |
| Single VM pass-pair #1, job 122123019097 | Reference | 12,517 ms | 3,705 ms | 1,916 ms | 1,949 ms |
| Single VM pass-pair #2 (job rerun), job 122124175703 | CPE | 4,217 ms | 17,100 ms | 1,418 ms | 3,457 ms |

Both single-VM repetitions used AB/BA or BA/AB counterbalancing; each
arm executed twice per single-VM repetition (6 attempts, 60 capped hits).
Parallel jobs each executed once (3 attempts, 30 capped hits).
The in-memory collector caps results at ten records per query, so these
reported hit totals are **saturated hard limits**, not independent coverage
or accuracy measures. Both sequential controls observed zero shared URL
proxy matches between the two *synthetic* query families; URL overlap
does not establish an absence of shared upstream source ancestry.

**Key finding:** The larger wall-time cost switched between arms when the
random initial order switched. This is consistent with Docker image pull,
warm cache and provider-startup/order effects. It is not proof of a causal
performance benefit for either architecture. Query latency also varied
with unobserved provider/network conditions. The next source revision adds
explicit image pull, provider readiness and build time to distinguish
cold-start components; qualify that revision independently before using
those fields.

**Provisional decision:** Retain two physically separate GHA runners as
the primary execution/custody arrangement. Maintain randomized,
counterbalanced single-runner sequential operation as a diagnostics
control. Do not declare a superiority in scientific retrieval quality.

## Cold-start decomposition — instrumented native rep

The corrected timing-instrumented head
`6c78c87f17ed79462425d13911d870732c013854`

All five qualification jobs passed. Parallel jobs reference/CPE each issued

| --- | ---: | ---: | ---: | ---: | ---: |
| Distinct VM reference | 5,923 | 2,296 | 14,952 | 1,579 | 25,010 |
| Distinct VM CPE-labelled | 4,053 | 2,270 | 16,043 | 1,877 | 24,466 |
| Single VM first pass reference (cold) | 6,685 | 2,267 | 18,523 | 2,636 | 31,007 |
| Single VM first pass CPE (warm) | 319 | 1,179 | 255 | 1,849 | 3,815 |
| Single VM second pass reference (warm) | 202 | 2,172 | 268 | 1,391 | 4,325 |
| Single VM second pass CPE (warm) | 188 | 2,233 | 274 | 1,927 | 4,929 |

**Observed primitive:** most of the apparent slow-first-arm effect is
one-time Go compilation and Docker image pull, **not retrieval time**.
A fresh container does not require a fresh download/rebuild; caching
persists on the same VM. Distinct VMs incur their own compilation/pull.
Provider-ready time still varies between fresh SearXNG containers.

The number of distinct source hosts also changed between otherwise
identical arm repetitions (reference 27 then 25; CPE 27 then 28).
Source availability/timing/engine variability is real. With 10 hits
capped per query, **these runs cannot distinguish semantic recall or
coverage quality**; all capped hit totals equal 30 per arm pass. To
compare relevance or coverage later, vary top-k only through a separately
reviewed and fixed evidence budget and independently adjudicated sources.

**Engineering conclusion:** if minimizing per-run wall-clock time for
small synthetic workloads, prebuild the Go worker once and pre-pull the
pinned provider image per VM, then create fresh SearXNG containers.
This reduces setup confounding; it does **not** obviate two independent
VMs where source custody and blind separation matter. Our primary
architecture remains separate GitHub-hosted runners, with the
single-VM counterbalanced control retained in native CI.

## Prewarmed VM optimization — 2026-10-27

The implementation now has an **explicit one-time runner preparation stage**
(`tools/concept-sweep/prepare_runner.sh`), qualified on public native
[run 40506152579](https://github.com/SemperSupra/agent-dispatch/actions/runs/40506152579).
It pulls only the exact pinned SearXNG image and compiles one Go collector
binary to a fixed runner-local path **once per VM**, then uses a fresh Docker
container for every arm/pass.

The prepared binary and image are confined to the ephemeral VM, never
uploaded or passed between Track A and Track B. The per-arm launcher refuses
prewarm unless `MCP_GHA_TOPOLOGY_SYNTHETIC_ONLY=1` and validates the
one-time receipt's native run ID, run attempt, source SHA, pinned image
digest and SHA256 of the actual compiled executable. The native independent
runner jobs deliberately altered both the source-SHA and binary-SHA fields;
**both spoofed receipts were denied before any search**.
Do not confuse this with a genuine trusted-execution attestation; it is
local custody and replay protection for the public synthetic qualification.

All **five** Stage-R/topology native jobs passed: two physically separate
GHA arms, one counterbalanced four-container single-VM diagnostic, source
negative tests and pinned real SearXNG probe. The real provider accepted
**18/18 search requests**; the result metadata remains synthetic-only,
not CPE-validated. A separate MCP worker regression was also queued for
this source change; its own native result is tracked separately.

| Prewarmed worker | One-time image pull | One-time Go build | Arm runtime (including fresh container start/search) | Requests |
| --- | ---: | ---: | ---: | ---: |
| Separate VM reference | 4.831 s | 15.364 s | 5.341 s | 3/3 succeeded |
| Separate VM CPE-labelled | 5.317 s | 25.759 s | 5.325 s | 3/3 succeeded |
| Single VM sequential (all four passes) | 4.861 s | 11.538 s | 4.83 s reference mean; 4.83 s CPE mean | 12/12 succeeded |

In the corrected receipt, `image_pull_ms=0` and `go_build_ms=0`
for each **prewarmed arm**, because no such operations occurred during
the arm. Image presence verification is measured separately.
One-time preparation metrics remain independently visible.
Do not interpret post-preparation arm time as end-to-end time from a
cold GitHub-hosted VM. Image pulls and Go builds are still necessary on
each **distinct** ephemeral VM; their durations vary with host load.

This is an operational optimization, not a scientific improvement to
search-result relevance. Because all queries still return the maximum
10 stored hits per request, the capped counts are unsuitable as recall
or concept novelty scores. Retain the private reference/CPE two-track
authority and source-custody gates.

## Next scientific qualification

For a real paired study, prefreeze two **independently generated** plans,
authenticate true CPE query projection, separate all sensitive task/answer
context under sealed private-workcell custody, and run both approved
retrieval arms in temporary runners that are actually authorized to see
their inputs. After the private re-intake, use the canonical private
Stage R/Stage P protocol and CPE #229 adjudication. Repeat topology
comparisons across enough independently randomized runs to estimate
source/provider and time/host variance; only then consider changing the
default topology.
