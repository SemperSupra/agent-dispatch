# R69 native GitHub Actions artifact custody (public-only)

Two separate GitHub-hosted CI jobs run under a public pull request. A **producer** writes one synthetic JSON receipt (public repository, native run ID/attempt, public source SHA and event) and uploads it using a SHA-pinned official `actions/upload-artifact` release with 1-day retention. A distinct **consumer** uses only `actions:read` to retrieve the native run record, artifact metadata and artifact ZIP through GitHub's official REST endpoints. It checks exact run/source identity, artifact ID/name, SHA-256 digest, a single safe JSON member and the original receipt's identity. It never dispatches another workflow or accesses private source.

To prevent credential forwarding to storage-CDN redirects, the consumer refuses redirects at the authenticated API request and issues a **new uncredentialed request** only to a validated HTTPS artifact CDN host. Unknown redirect origins HOLD rather than widening access. Empty, duplicate, expired, stale-attempt, mismatched digest/HEAD and unsafe ZIP layouts fail closed. Offline negative tests are stdlib Python; use `python3 -m unittest discover -s experiments/fencing/artifact-r69 -p 'test_*.py' -v`.

**Qualification ceiling:** this is real provider-native artifact upload and cross-job readback, not a trusted Agent Dispatch result receiver, independent signer, externally monotonic witness, effect-side fence, durable indefinite storage, or lost-ACK recovery when the run ID is unknown. Only public synthetic values occur in the artifact; all PR sources and workflows remain unmerged.

## R70 — Native workflow-run candidate discovery (read-only)

After the independent artifact consumer verifies the known-run receipt, `python3 experiments/fencing/artifact-r69/discover.py --native` obtains its own workflow ID through a native read-only run GET, then performs a **separate native workflow-runs LIST query using only workflow ID, public pull-request HEAD SHA, and event**—not the run ID. The previously known run ID is used only as an independent oracle to verify the listed candidates include this run. A unique snapshot is classified `ONE_CANDIDATE_AT_READBACK`; several candidates are `AMBIGUOUS_MULTIPLE_CANDIDATES_HOLD`; a missing, cross-scope, duplicate, paginated or inconsistent result must HOLD. The exact API list may be eventually consistent and a one-candidate snapshot does **not** prove the request was the one started by an earlier dispatch, or enable safe blind resubmission after lost ACK. Run the same offline unittest discovery command; `test_discover.py` covers the ambiguity/negative oracles. No action is dispatched, restarted or cancelled.
